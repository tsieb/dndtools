# Screens parity inventory — the three run surfaces before conversion

RC-CAN-7.5. This is the pre-conversion record of what the Command Center (`/`), the GM screen board
(`/board`) and the Session console (`/session`) do **as they ship today**, so
[ADR-041](../adr/041-screens-as-the-run-surface.md)'s conversion can be checked row by row instead of
by impression. RC-CAN-7.6 and RC-CAN-7.8 tick these rows; RC-WID-5.1–5.4 close the gaps §4 records.

This document describes the implementation, not the target. Nothing here is a commitment that a row
survives conversion unchanged — that is what the acceptance criteria of 7.6 and 7.8 are for.

### What an aria snapshot here covers

Each snapshot is `page.locator('#main-content').ariaSnapshot()` — the **route's own** accessibility
tree. The app shell around it (the `<h1>` in the top bar, the sidebar, the rail, the phone tab bar,
the command palette, the quick panel, the Host and projection controls) is deliberately excluded: it
is owned by RC-CAN-7.4, RC-UX-4.2/4.3 and RC-POL-1.23, not by this conversion. Two consequences:

- Every route's `<h1>` lives in `app/shell/TopBar.tsx` and is the section title from `app/nav.ts`
  (`nav.commandCenter`, `nav.gmScreen`, `nav.session`, each rendered through the active system
  package's vocabulary — "DM screen" under 5e, "GM screen" under Generic). The in-route headings
  below therefore start at `<h2>`.
- Dialogs render outside `#main-content`, so the three dialog snapshots are `body` snapshots and are
  named `aria-dialog-*.yaml`.

### Reading the parity target column

| Target       | Meaning                                                                                                |
| ------------ | ------------------------------------------------------------------------------------------------------ |
| **builtin**  | A widget body already exists in `app/widgets/builtin/` and the row is a re-parent, not a rebuild.      |
| **template** | The row can be expressed by a widget `template` definition — today's eight kinds, or one WID-5.3 adds. |
| **gap→X**    | No public surface can express the row; story X closes it. Every gap is registered in §4.               |
| **shell**    | Not a widget: the row belongs to the screen chrome or the app shell, and another story owns it.        |

Today's public surface, for reference: eight template kinds (`data-table`, `status-list`, `tracker`,
`action-panel`, `scene-message`, `chart`, `stat-block`, `form-panel`), eight query sources
(`current-combatants`, `visible-characters`, `selected-scene`, `session-state`, `notes`, `maps`,
`content-objects`, `binding`), and command descriptors whose output destinations are `scene`,
`session`, `entity`, `player-visible-state`, `player-scene`, `clipboard`, `network`,
`exported-package` — see `packages/core/src/state/widget-package-state.ts`. There is **no**
navigation or creation destination, which is why so many hub rows below land on `gap→WID-5.1`.

### 2.3 Heading and keyboard structure at `/board`

`h1` (shell) → `h2` "GM Screen". **No other heading** — the seven tiles are `group`s named by their
frame, not headings, so a screen-reader GM cannot navigate the board by heading or rotor. Traversal
is by the core's `focusOrder`, not by DOM position. Reproducing this in flow (CAN-7.7) must not make
it worse; the flow policy's reading-order requirement is the fix, and it is not satisfied by canvas's
current z-order/pin traversal (ADR-041).

### 2.4 Tier behaviour at `/board`

The bounded canvas derives its fit scale from the available width, so on a 390px phone the authored
3-column layout renders at ≈0.45 and **the third column is cut off horizontally** while the surface
scrolls both axes; tile body text in Prep and Quick Reference is not readable at that scale (see
`board-phone-tavern.webp`). Desktop and rail are identical in the aria tree. The phone Initiative
tile additionally drops to its reduced variant (BD-21). The repo's own browser baseline already
records a mobile axe `target-size` failure on this route
(`state/RC-DSN-2.2.browser-baseline.md`, "Board axe, mobile"), which predates this story and is not
introduced by it. This is the concrete case CAN-7.7's flow policy and §1.6 D5 exist to answer.

## 3. Session (`/session`)

Source: `apps/gm-react/src/screens/session/`. Layout: `<Page max={1280}>`, a lifecycle header, an
optional standby card, then a `1.6fr / 1fr` grid with the combat panel on the left and a stacked
column of eleven panels on the right. Evidence: `aria-session-{desktop,rail,phone}.yaml` (Standby),
`aria-session-desktop-{prep,active,recap}.yaml`, `aria-session-desktop-live-combat.yaml`,
`aria-session-phone-live-combat.yaml`, `aria-session-desktop-rest-timeline.yaml`,
`aria-session-desktop-recap-preview-player.yaml`, `aria-session-phone-recap.yaml`, and the three
`aria-dialog-*.yaml` files.

The whole screen has four gate axes that every row is a function of: **workflow**
(`idle`/`prep`/`active`/`recap`), **isDm**, **previewing**, and the per-panel emptiness of its read.
Disabled controls carry the reason inside the accessible name — "Build encounter (unavailable — go
live first)" off-session, "(unavailable — exit player preview first)" while previewing. That pattern
is load-bearing and has no public equivalent today (G-07).

### 3.5 Heading and tier structure at `/session`

**Heading order (DM, Standby):** `h1` (shell) → `h2` Combat → `h3` "Go live to start combat" → `h2`
Dice → `h2` Rollable tables → `h3` "No rollable tables yet." → `h2` Handouts → `h2` Now playing →
`h2` Stage → `h2` Campaign date → `h2` Prep & recap → `h2` End-of-session capture → `h2` Table
roster → `h2` Party → `h2` Schedule next session. The lifecycle header (SE-01–SE-06) contributes no
heading, so the first thing a heading-navigating GM reaches is Combat, not the session's own state.
`h3` is used only for empty states. In Recap, `h2` "Rests this session" appears between Party and
Schedule when the rest log is non-empty.

**Tier behaviour at `/session`:** the only branch is `viewport === 'phone'`, collapsing the
`1.6fr / 1fr` grid to one column. The accessibility tree is otherwise **identical at all three
tiers**, including the full initiative list with every per-combatant control — verified by diffing
`aria-session-desktop.yaml` against `-rail` and `-phone`, and `aria-session-desktop-live-combat.yaml`
against `aria-session-phone-live-combat.yaml`. Unlike `/board`, nothing is dropped on a phone.

**Screenshots:** `session-{desktop,rail,phone}-{tavern,parchment,high-contrast}.webp` (Standby),
`session-desktop-{prep,active,recap}.webp`, `session-{desktop,phone}-live-combat.webp`,

### 4.2 Gaps with no story yet — proposed

These five are the reason CAN-7.6's precondition is not yet met. **They are proposed here, not
filed:** `docs/planning/RC_ROADMAP.md` is outside this story's `Owns:`, so inserting them into §6
(Workstream WID) and the §23 story index, and re-running `tools/roadmap/sync-tasks.py`, is an owner
step. The text below is written in the roadmap's story format so filing is a copy.

- **RC-WID-5.6 — Widget-owned dialogs and confirmations.** `M` · P2 · Deps: 5.1 · Owns:
  `packages/core/src/state/widget-package-state.ts`, `packages/core/src/schemas/widget-package.ts`,
  `apps/gm-react/src/app/widgets/hostBridge.ts`,
  `apps/gm-react/src/app/widgetBuilder/CommandsStep.tsx`, `docs/architecture/WIDGETS.md`. Six
  controls on the Session screen do not act — they raise a modal the widget owns, and four of those
  modals guard an irreversible write: start a session (SE-30), call a rest (SE-31), end the session
  (SE-32), end combat (SE-33), pick a condition (SE-13) and adjust hit points (SE-12). WID-5.1's
  intents open a destination; none of them can open a dialog, collect a choice and dispatch a
  command with it. Add a declarative dialog descriptor: a title, a description, a closed set of
  fields drawn from the widget's own query sources, and one or more actions each bound to an
  existing command descriptor and marked ordinary or danger. The host owns focus trapping, Escape,
  the danger styling and the actor gate, so a widget cannot raise a dialog for a write the core will
  then refuse. Acceptance: a builder-made action panel raises a two-action confirm and dispatches
  the chosen command; a danger action renders as the existing danger confirm; the dialog is
  unreachable for an actor the command's gate refuses; WIDGETS.md documents the descriptor.
- **RC-WID-5.7 — Declarative gating, disabled reasons and live regions.** `M` · P2 · Deps: 5.2 ·
  Owns: `packages/core/src/state/widget-package-state.ts`,
  `packages/core/src/schemas/widget-package.ts`, `apps/gm-react/src/app/widgets/templates`,
  `apps/gm-react/src/app/widgetBuilder/CommandsStep.tsx`, `docs/architecture/WIDGETS.md`. Both run
  surfaces gate controls on session workflow, DM-ness and preview, and **every** gated control
  carries the reason inside its accessible name ("Roll d20 — Go live in Session first — this reaches
  the table only during play.", "Build encounter (unavailable — exit player preview first)"). They
  also announce durable outcomes through `role="status"` regions the panel owns — the combat turn
  announcement, the reorder announcement, the board's status and alert regions. A template widget
  can declare neither. Add a gate expression over the session-state and actor query sources, with a
  required reason string per gate, and a declared polite live region a command descriptor can write.
  Acceptance: a gated builder-made control is disabled with its reason in the accessible name at
  every tier; the gate is re-evaluated on a workflow change without a remount; an axe run finds no
  name-role-value violation on the gated control; a declared announcement reaches a screen reader
  once per dispatch, not once per render; WIDGETS.md records both.
- **RC-WID-5.8 — Declared keyboard models.** `M` · P3 · Deps: 5.3 · Owns:
  `packages/core/src/state/widget-package-state.ts`,
  `packages/core/src/schemas/widget-package.ts`, `apps/gm-react/src/app/canvas/WidgetFrame.tsx`,
  `apps/gm-react/src/app/widgets/hostBridge.ts`, `docs/architecture/WIDGETS.md`. The combat tracker
  binds a bare-key model on `window` (`n`/`p` turn, `d`/`h` HP keypad, arrows to move the row
  cursor, `Enter` into the detail panel, `Alt+Arrow` to reorder), refused while a text field or a
  dialog owns the keyboard. A GM-built widget has no way to declare one, so SE-10–SE-12 cannot be
  rebuilt without losing the fastest path through a live fight. Add a declared key map — key,
  modifier, the command or intent it runs, and its help text — arbitrated by the host so two widgets
  on one screen cannot claim the same key silently and so the same text-field and dialog refusals
  apply everywhere. Acceptance: a builder-made tracker advances the turn on `n`; a conflicting
  second declaration is reported at install, not at press; the keys are listed in the help surface;
  typing in a widget's own textbox never triggers them.
- **RC-WID-5.9 — Multi-select and roster picking over a query source.** `S` · P3 · Deps: 5.2 ·
  Owns: `apps/gm-react/src/app/widgets/templates/FormPanel.tsx`,
  `apps/gm-react/src/app/widgetBuilder/DataStepBindings.tsx`,
  `packages/core/src/schemas/widget-package.ts`. `form-panel` has no field type that renders a query
  source as a selectable set. The end-of-session capture's "What changed" checkbox group over 14
  vault items (SE-22), and the encounter builder's roster toggles (SE-14), both need one. Add a
  multi-select field bound to a query source, whose submitted value is a list of entity ids the
  host re-checks against the actor's read gate before the command sees it. Acceptance: a
  builder-made form submits a chosen subset; an id the actor may not read is dropped and audited;
  the builder previews the field against live data.
- **RC-WID-5.10 — A labelled region and heading for a bare widget.** `S` · P3 · Deps: 5.3 · Owns:
  `apps/gm-react/src/app/canvas/WidgetFrame.tsx`, `apps/gm-react/src/app/widgets/templates`,
  `docs/architecture/WIDGETS.md`. Today `/board` has exactly one heading for seven tiles and the
  hub's player and observer variants have none at all (CC-14/CC-15), while `/session` gets its
  navigability from a real `<h2>` per panel. WID-5.3's bare presentation hides the frame's title bar
  in view mode, which would delete the Session headings on conversion unless a bare widget can
  contribute a heading of a declared level to the screen's outline. Add that, with the host
  validating that a screen's headings do not skip a level. Acceptance: a bare widget renders a
  labelled region and a heading at its declared level; a screen whose widgets would skip a level
  fails a test; the Session screen's heading order after CAN-7.8 matches §3.5 of this document.

## 5. What this inventory does not cover

Stated plainly so CAN-7.6 and CAN-7.8 do not mistake silence for coverage.

- **Loading states.** No row records one. The routes reach `runtime.loaded` fast enough locally that
  the harness could not hold a loading frame deterministically; the board's own
  "Setting up your GM Screen…" state and the lazy route-chunk boundary are inventoried from source
  only. RC-DSN-3.4 owns the skeleton and progress states these should adopt.
- **Populated states for four panels.** Rollable tables (SE-16), session archives and the recap
  editor with real archives (SE-21), the capture form against an existing archive (SE-22), and a
  configured Google Calendar (SE-26) are all empty in the demo seed and are described from source.
- **Three dialogs and two sheets.** End combat (SE-33), the condition picker (SE-13) and the HP
  keypad sheet (SE-12) have no aria snapshot here.
- **The board's layout-quality indicator** (BD-09) never renders on the seeded layout.
- **The player and observer variants of `/board` and `/session`** were captured through the DM's
  `enterPreview` seam, not from a second device with its own actor. The read path is the same
  actor-filtered one, but a real participant device is not proven by this capture.
- **The Session player preview** (`aria-session-desktop-recap-preview-player.yaml`) was taken while
  the workflow was `recap`, not `active`, because the capture drove the lifecycle in order. Its
  gate text therefore mixes the preview reason and the recap reason.
- **Locale and system package.** Everything was captured in `en` under the default package. Every
  string above is a message key in the source; the `{gm}`/`{player}` placeholders resolve through
  the active package, so the literal words ("DM screen") are not part of the parity contract.
- **Density and motion.** Captured at the default density for each tier (`expanded` → `standard`,
  otherwise `comfortable`) and default motion. Reduced motion changes CC-04's pulse and the frame
  transitions; it was not captured.
- **Performance.** No `scene-first-render` measurement was taken here. CAN-7.6 carries that budget.
