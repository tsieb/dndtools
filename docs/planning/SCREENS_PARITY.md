# Screens parity inventory — the three run surfaces before conversion

RC-CAN-7.5. This is the pre-conversion record of what the Command Center (`/`), the GM screen board
(`/board`) and the Session console (`/session`) do **at the reviewed source baseline**, with historical and refreshed evidence distinguished below, so
[ADR-041](../adr/041-screens-as-the-run-surface.md)'s conversion can be checked row by row instead of
by impression. RC-CAN-7.6 and RC-CAN-7.8 tick these rows; RC-WID-5.1–5.4 close the gaps §4 records.

This document describes the implementation, not the target. Nothing here is a commitment that a row
survives conversion unchanged — that is what the acceptance criteria of 7.6 and 7.8 are for.

### What an aria snapshot here covers

Each snapshot is `page.locator('#main-content').ariaSnapshot()` — the **route's own** accessibility
tree. The app shell around it (the `<h1>` in the top bar, the sidebar, the rail, the phone tab bar,
the command palette, the quick panel, the Host and projection controls) is deliberately excluded: it
is owned by RC-CAN-7.4, RC-UX-4.2/4.3 and RC-POL-1.23, not by this conversion. Two consequences:

- Every route's `<h1>` lives in `app/shell/TopBar.tsx` and is the section title from `app/nav.ts`
  (`nav.commandCenter`, `nav.gmScreen`, `nav.session`, each rendered through the active system
  package's vocabulary — "DM screen" under 5e, "GM screen" under Generic). The in-route headings
  below therefore start at `<h2>`.
- Dialogs render outside `#main-content`, so the three dialog snapshots are `body` snapshots and are
  named `aria-dialog-*.yaml`.

### Reading the parity target column

| Target       | Meaning                                                                                                                  |
| ------------ | ------------------------------------------------------------------------------------------------------------------------ |
| **builtin**  | A related body exists in `app/widgets/builtin/`; inspect its scope before reuse. It is not proof of full Session parity. |
| **template** | The row can be expressed by a widget `template` definition — today's eight kinds, or one WID-5.3 adds.                   |
| **gap→X**    | No public surface can express the row; story X closes it. Every gap is registered in §4.                                 |
| **shell**    | Not a widget: the row belongs to the screen chrome or the app shell, and another story owns it.                          |

Today's public surface, for reference: eight template kinds (`data-table`, `status-list`, `tracker`,
`action-panel`, `scene-message`, `chart`, `stat-block`, `form-panel`), eight query sources
(`current-combatants`, `visible-characters`, `selected-scene`, `session-state`, `notes`, `maps`,
`content-objects`, `binding`), and command descriptors whose output destinations are `scene`,
`session`, `entity`, `player-visible-state`, `player-scene`, `clipboard`, `network`,
`exported-package` — see `packages/core/src/state/widget-package-state.ts`. There is **no**
navigation or creation destination, which is why so many hub rows below land on `gap→WID-5.1`.

### 2.3 Heading and keyboard structure at `/board`

`h1` (shell) → `h2` "GM Screen". **No other heading** — the seven tiles are `group`s named by their
frame, not headings, so a screen-reader GM cannot navigate the board by heading or rotor. Traversal
is by the core's `focusOrder`, not by DOM position. Reproducing this in flow (CAN-7.7) must not make
it worse; the flow policy's reading-order requirement is the fix, and it is not satisfied by canvas's
current z-order/pin traversal (ADR-041).

### 2.4 Tier behaviour at `/board`

The bounded canvas derives its fit scale from the available width, so on a 390px phone the authored
3-column layout renders at ≈0.45 and **the third column is cut off horizontally** while the surface
scrolls both axes; tile body text in Prep and Quick Reference is not readable at that scale (see
`board-phone-tavern.webp`). Desktop and rail are identical in the aria tree. The phone Initiative
tile additionally drops to its reduced variant (BD-21). The repo's own browser baseline already

## 5. What this inventory does not cover

Stated plainly so CAN-7.6 and CAN-7.8 do not mistake silence for coverage.

- **Loading states.** No row records one. The routes reach `runtime.loaded` fast enough locally that
  the harness could not hold a loading frame deterministically; the board's own
  "Setting up your GM Screen…" state and the lazy route-chunk boundary are inventoried from source
  only. RC-DSN-3.4 owns the skeleton and progress states these should adopt.
- **Uncaptured populated states.** Rollable tables (SE-16), delivered handouts (SE-17),
  playing audio (SE-18), a staged map (SE-19), and configured Google Calendar (SE-26) are described
  from source only. Recap does contain an archive, its recap editor (SE-21), and the capture form
  with 14 checkboxes (SE-22); no successful save is proven by these snapshots.
- **Uncaptured dialogs and sheets.** Start a session (SE-30), end combat (SE-33), the condition picker (SE-13) and the HP
  keypad sheet (SE-12) have no aria snapshot here.
- **The board's layout-quality indicator** (BD-09) never renders on the seeded layout.
- **The player and observer variants of `/board` and `/session`** were captured through the DM's
  `enterPreview` seam, not from a second device with its own actor. The read path is the same
  actor-filtered one, but a real participant device is not proven by this capture.
- **The Session player preview** (`aria-session-desktop-recap-preview-player.yaml`) was taken while
  the workflow was `recap`, not `active`, because the capture drove the lifecycle in order. Its
  gate text therefore mixes the preview reason and the recap reason.
- **Locale and system package.** Everything was captured in `en` under the default package. Every
  string above is a message key in the source; the `{gm}`/`{player}` placeholders resolve through
  the active package, so the literal words ("DM screen") are not part of the parity contract.
- **Density and motion.** Captured at the default density for each tier (`expanded` → `standard`,
  otherwise `comfortable`) and default motion. Reduced motion changes CC-04's pulse and the frame
  transitions; it was not captured.
- **Performance.** No `scene-first-render` measurement was taken here. CAN-7.6 carries that budget.
