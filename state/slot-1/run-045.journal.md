## Decisions

- A denied MCP tool call records NO audit entry today (`agentDenied` in
  packages/core/src/mcp/agent-dispatch.ts:106 returns `nextState: state` unchanged) even though
  `McpAuditEntry.mode` (packages/core/src/state/mcp-policy.ts:196) types `'denied'` as a value.
  This is existing Core behavior, out of this story's Owns (settings AI, not mcp-policy commands) —
  did NOT change it. The audit browser still supports filtering/rendering a `'denied'` entry (dead
  code path today, forward-compatible), and e2e coverage exercises the two outcomes the pipeline
  actually produces: staged and direct/committed.
- Export ships the full unfiltered trail regardless of the browser's active filter — an audit
  export silently narrowed by whatever filter was last clicked would be a real compliance footgun.
- Batch controls (filters, checkboxes, "Approve selected"/"Reject selected") only render when
  `pending.length > 1` (apps/gm-react/src/screens/settings/AiBatchReview.tsx:98). Found via a real
  regression: with exactly one proposal, the always-disabled "Approve selected" button was matched
  by the pre-existing RC-AI-2.2 conflict spec's `getByRole('button', { name: 'Approve' })` (default
  non-exact substring match) even while conflicted-and-un-approvable — asserting a dead control
  existed. Gating avoids the collision and the clutter.
- Batch approve computes `conflictOf` per selection and silently skips conflicted proposals
  (summary toast reports `skipped` folded into `failed`); batch reject has no such exclusion since
  rejecting a conflicted proposal is identical to rejecting any other pending one.
